# AI Diagnostic API Analysis & Implementation Plan (Milestone M2)

## Executive Summary
This document provides a comprehensive codebase audit and implementation plan for the **Milestone M2: AI Diagnostic API** for the Kabroda Quantitative Crypto Trading System. The objective is to build five robust system management JSON endpoints under `/api/v1/system/*` to expose live system state, trades, parameters registry, errors, and ad-hoc AI-driven system analyses.

---

## 1. Parameters Definition, Tracking, and Storage (Objective 2)

The Kabroda system currently uses a hybrid approach of hardcoded defaults, configuration JSON, environment variables, and specialized database tables for parameter management:

### A. Configuration JSON File (`krown_settings_and_rules.json`)
* **Location**: `/bold-hubble/krown_settings_and_rules.json`
* **Status**: Static documentation and validation reference. It is **not** imported or read at runtime by the active strategy execution pipelines or indicator calculation routines.
* **Contents**: Outlines default settings for `BBWP`, `PMARP`, `RSI`, and basic SMA values, along with descriptive execution rules for Strategies 1–5.
* **Usage**: Accessed strictly by `bold-hubble/kqal/system_auditor.py` (lines 31, 184) to compare active parameters and report discrepancies.

### B. Hardcoded Parameters in Indicators and Strategies
The active trading and decision paths define calculations and thresholds directly within the Python code:
* **BBWP (Bollinger Band Width Percentile)**:
  * Defined in `battlebox_pipeline.py` (lines 226–246).
  * Hardcoded calculation parameters: `bb_period = 20`, `bb_std = 2.0`, `lookback = 252`.
  * Hardcoded thresholds in `_bbwp_state_label` (lines 268–273): 
    * `EXTREME_COMPRESSION`: `<= 5.0`
    * `MODERATE_COMPRESSION`: `<= 15.0`
    * `HIGH_EXPANSION`: `>= 85.0`
    * `EXTREME_EXPANSION`: `>= 95.0`
* **PMARP (Price MA Ratio Percentile)**:
  * Defined in `battlebox_pipeline.py` (lines 249–265).
  * Hardcoded calculation parameters: `ma_period = 50`, `lookback = 252`.
  * Hardcoded thresholds in `_pmarp_state_label` (lines 276–281):
    * `EXTREME_DEPRESSED`: `<= 5.0`
    * `MODERATE_DEPRESSED`: `<= 15.0`
    * `MODERATE_OVEREXTENDED`: `>= 85.0`
    * `EXTREME_OVEREXTENDED`: `>= 95.0`
* **RSI (Relative Strength Index)**:
  * Standard 14-period RSI is used across timeframes. Thresholds are typically `70.0` (overbought) and `30.0` (oversold).
* **ATR Multipliers and Safety Rails**:
  * Hardcoded inside `gravity_engine.py` during candidate detection and stop/target formulation:
    * **4H Timeframe** (lines 602–680):
      * Stop-loss: Nearest pivot +/- `0.25 * ATR14`.
      * ATR Fallback: `1.5 * ATR14` from entry.
      * Floor limit: `1.5 * ATR14` (triggers `target_too_small_flag = True` if lower).
      * Cap limit: `3.0 * ATR14` (if calculated leg exceeds `5.0 * ATR14`).
    * **1H Timeframe** (lines 829–909):
      * Stop-loss: Nearest pivot +/- `0.25 * ATR14`.
      * ATR Fallback: `1.0 * ATR14` from entry.
      * Floor limit: `1.0 * ATR14` (triggers `target_too_small_flag = True` if lower).
      * Cap limit: `3.0 * ATR14` (if calculated leg exceeds `5.0 * ATR14`).
  * **Fibonacci Targets**: Multipliers for take-profits are hardcoded at `1.0x` (T1), `1.618x` (T2), and `2.618x` (T3) of the entry-to-stop leg distance.

### C. Environment Variables (Position Sizing)
Read at module load time in `bold-hubble/position_sizing/position_sizing.py`:
* `REFERENCE_ACCOUNT_BALANCE`: Reference balance used for theoretical contract sizes (defaults to `"10000"`).
* `RISK_PERCENT`: Percentage of capital risked per trade (defaults to `"0.02"` / 2%).
* `POSITION_SIZING_METHOD`: Dispatcher key (defaults to `"volatility"`, supports `fixed_fractional`, `kelly`).

### D. Parameter Database Tables
There is no mutable system parameter registry table. Only two tables store system-level settings:
* `lti_protocol` (mutable single row): Stores long-term investing configurations (`universe`, `conviction_threshold`, `drawdown_protocol`, `cash_floor_pct`, `residual_trim_pct`).
* `monitor_config` (mutable single row): Stores notification gate parameters (`gate_a_min_events`, `gate_b_harness_reviewed`, `notification_enabled`, `confirmation_polls`, `cooldown_hours`).

## 2. Active Sessions and Shadow Runners Queries (Objective 3)

Active trading sessions and shadow runners can be queried from the database using SQLAlchemy against the `SessionLock` and `CampaignLog` tables:

### A. Active Sessions
A session can be considered active in two contexts:
1. **Active Session Lock**: An active, locked trading window (e.g., the daily NY Futures lock) generated by the system.
   * **Table**: `SessionLock` (`session_locks`)
   * **SQLAlchemy Query**:
     ```python
     from database import SessionLock
     import datetime

     today_str = datetime.datetime.utcnow().strftime("%Y-%m-%d")
     active_lock = db.query(SessionLock).filter(
         SessionLock.symbol == "BTC/USDT",
         SessionLock.session_id == "us_ny_futures",
         SessionLock.date_key == today_str
     ).first()
     ```
2. **Active Campaign / Position**: A trade campaign that has been approved and is either waiting for entry fill or is currently in-trade (unresolved).
   * **Table**: `CampaignLog` (`campaign_logs`)
   * **SQLAlchemy Query**:
     ```python
     from database import CampaignLog
     
     active_campaigns = db.query(CampaignLog).filter(
         CampaignLog.is_canonical == True,
         CampaignLog.closed_at.is_(None)
     ).all()
     ```
     * Note: APPROVED but unfilled campaigns will have `entry_filled_at.is_(None)` while active positions will have `entry_filled_at.isnot(None)`.

### B. Active Shadow Runners
Shadow runners trail a stop-loss using specialized rules (15M EMA21 trail or 4H/1H structural zone trail) for statistical counterfactual tracking without affecting real capital.
* **Table**: `CampaignLog` (`campaign_logs`)
* **SQLAlchemy Query**:
  ```python
  from database import CampaignLog

  active_shadow_runners = db.query(CampaignLog).filter(
      CampaignLog.is_canonical == True,
      CampaignLog.shadow_runner_active == True,
      CampaignLog.shadow_runner_closed_at.is_(None)
  ).all()
  ```

## 3. System Errors and Alerts Tracking (Objective 4)

Errors and notifications are tracked across standard logs, agent run logs, and SMTP channels:

### A. Global Exception Handler
* In `main.py` (lines 1964–1977), `global_exception_handler` intercepts unhandled HTTP and application errors.
* It prints critical crash details to the standard error console (`print(f"CRITICAL CRASH:\n{error_trace}")`) and outputs a fatal HTML crash page (HTTP 500) to human dashboard visitors.
* Schedulers catch internal exceptions inside their loops to prevent crashing background tasks from terminating the entire FastAPI server.

### B. Agent Core Error Tracking
* When an LLM invocation (via `agent_core.py`) fails, a run record is inserted into the database.
* **Table**: `AgentRunLog` (`agent_run_log`)
* **Filters**: `AgentRunLog.status == 'ERROR'`
* **Fields**: `error_message` holds the exception traceback or API error string.

### C. System Alert Notifications
* Candidate opens and exits are alerted via standard SMTP email.
* **Module**: `notify.py`
* **Recipient**: Defined by the `SMTP_DEST` environment variable.
* **Behavior**: Non-blocking. Invocations in `gravity_engine.py` and `ledger_closing_engine.py` are wrapped in try-except blocks so email transport failures do not block trade execution or database updates.

## 4. Scheduler Analysis and Health Tracking Design (Objective 5)

The Unified Server runs 6 distinct scheduler tasks registered in FastAPI's `lifespan` context:

| # | Scheduler Name | Frequency | Target / Behavior |
|---|----------------|-----------|-------------------|
| 1 | `senior_analyst` | Daily | Fires at `lock_end` (~9:00 AM ET / 14:00 UTC). Runs `kabroda_mas_flow.run_mas_analysis` (normal and recovery). |
| 2 | `jewel` | 6x Daily | ASIA_OPEN (01:00 UTC), ASIA_MIDDAY (05:00 UTC), LONDON_OPEN (09:00 UTC), NY_OPEN (14:00 UTC), NY_MIDDAY (18:00 UTC), NY_CLOSE (21:00 UTC). Runs `jewel_specialist.run_jewel_snapshot`. |
| 3 | `weekly` | Weekly | Sundays 23:00 UTC. Sequential execution of: (1) `elliott_wave_specialist`, (2) `performance_auditor`, (3) Audit-AI `harness.audit_runner` (H1-H6). |
| 4 | `daily_4h1h_audit` | Daily | 23:45 UTC. Invokes `audit_ai.run_daily_4h1h_audit` (H7-H9 kinematic/macro-bias checks and daily digests). |
| 5 | `outcome_tracker` | 4 Hours | Runs every 4 hours. Calculates 4H outcomes for `DecisionJournal` and closes canonical `CampaignLog.target_hit` values. |
| 6 | `monthly_lti` | Monthly | 1st of month 00:00 UTC. Runs Kraken monthly confluence audits (`lti_engine`). **Note**: Currently commented out in `lifespan` (marked as disabled). |

### Health Tracking Mechanism Design
Because these run as infinite async loops inside FastAPI tasks, their runtime health cannot be monitored externally without a tracking structure. We will introduce an **in-memory scheduler registry** on the FastAPI `app` instance.

#### A. Registry Structure
```python
# To be added to main.py
scheduler_health_registry = {
    "senior_analyst": {"last_run": None, "next_run": None, "status": "PENDING", "error_count": 0, "last_error": None},
    "jewel": {"last_run": None, "next_run": None, "status": "PENDING", "error_count": 0, "last_error": None},
    "weekly": {"last_run": None, "next_run": None, "status": "PENDING", "error_count": 0, "last_error": None},
    "daily_4h1h_audit": {"last_run": None, "next_run": None, "status": "PENDING", "error_count": 0, "last_error": None},
    "outcome_tracker": {"last_run": None, "next_run": None, "status": "PENDING", "error_count": 0, "last_error": None},
    "monthly_lti": {"last_run": None, "next_run": None, "status": "DISABLED", "error_count": 0, "last_error": None},
}
```

#### B. Update Protocol inside Scheduler Loops
Each scheduler in `main.py` will be modified to write its state directly into the registry:
1. **Calculation phase**: Just before sleeping, calculate `next_run` datetime using the wait seconds:
   ```python
   next_run_dt = datetime.now(timezone.utc) + timedelta(seconds=seconds)
   scheduler_health_registry["<name>"]["next_run"] = next_run_dt.isoformat()
   scheduler_health_registry["<name>"]["status"] = "WAITING"
   ```
2. **Wake-up phase**: Immediately after `sleep` wakes up:
   ```python
   scheduler_health_registry["<name>"]["status"] = "EXECUTING"
   ```
3. **Completion phase**: After successful task completion:
   ```python
   scheduler_health_registry["<name>"]["last_run"] = datetime.now(timezone.utc).isoformat()
   scheduler_health_registry["<name>"]["status"] = "WAITING"
   ```
4. **Exception handler**: Within the scheduler's outer `except Exception as e` block:
   ```python
   scheduler_health_registry["<name>"]["status"] = "ERROR"
   scheduler_health_registry["<name>"]["error_count"] += 1
   scheduler_health_registry["<name>"]["last_error"] = str(e)
   ```

## 5. Spec & Storage Design for `POST /api/v1/system/analysis` (Objective 6)

The `POST /api/v1/system/analysis` endpoint takes an ad-hoc natural language query, compiles a systemic data context block, runs the query against a designated Claude agent, and returns a structured diagnostic report.

### A. Database Storage Schema
A new database table is required to log queries and retain reports for dashboard visualization and auditability.

```python
# To be added to database.py
class SystemAnalysisReport(Base):
    __tablename__ = "system_analysis_reports"

    id = Column(Integer, primary_key=True, index=True)
    analysis_id = Column(String, unique=True, index=True, nullable=False) # UUID4
    query = Column(String, nullable=False)
    status = Column(String, default="PENDING", nullable=False) # PENDING | SUCCESS | FAILED
    report_json = Column(String, nullable=True) # Text representation of JSON report
    error_message = Column(String, nullable=True)
    created_at = Column(DateTime, default=datetime.datetime.utcnow)
```

### B. Agent Specification file (`agents/system_analysis.md`)
We will create a new agent spec containing YAML frontmatter and a prompt instructing Claude to return a structured JSON block:

```markdown
---
model: claude-sonnet-4-6
max_tokens: 4096
---
You are the Kabroda System Analyst Agent. Your task is to perform an ad-hoc diagnostic analysis of the trading system based on a user query and a provided database context.

Analyze system performance, parameter efficacy, structural levels, and errors. Your output MUST be valid JSON matching the following structure:
{
  "summary": "Detailed prose summary of your findings...",
  "verdict": "STABLE" | "OPTIMIZE" | "RISK_ALERT",
  "data_metrics": {
     "key_metric_1": value,
     "key_metric_2": value
  },
  "recommendations": [
    {
      "parameter": "Parameter name (e.g. BBWP moderate compression)",
      "observation": "What you noticed in the logs...",
      "suggestion": "Adjust from X to Y because..."
    }
  ],
  "confidence_score": 0.95
}
```

### C. Execution Flow
1. Client POSTs `{ "query": "Analyze win-rate under high vs low BBWP compression" }`.
2. Generate UUID `analysis_id` and insert a record with status `PENDING`.
3. Gather database context:
   * Current parameter values (hardcoded defaults + env vars + LtiProtocol).
   * Trade stats from the last 30 days (`CampaignLog`).
   * Performance Auditor summaries (`SystemAuditLog`).
   * Recent system anomalies or agent errors (`AgentRunLog`).
4. Invoke Claude via `agent_core._call_from_spec("system_analysis", context_text=query_and_db_context)`.
5. Parse the returned JSON, update the `SystemAnalysisReport` row (status `SUCCESS`, `report_json = raw_json`), and return it. On fail, update with status `FAILED` and populate `error_message`.

### 2. `GET /api/v1/system/trades`
Exposes canonical trading data and performance metrics over a selectable window.
* **Query Parameters**: `window` (one of: `7d` | `30d` | `all`, defaults to `30d`)
* **Authentication**: Required (is_logged_in == True)
* **SQL/Logic Steps**:
  1. Parse the `window` param. Construct `start_date` cutoff if `7d` or `30d`.
  2. Query `CampaignLog` filter on `is_canonical == True`, and `created_at >= start_date` if filtered. Order by `id.desc()`.
  3. Calculate metrics for the window matching standard formulas in `main.py` (overview route):
     * `win_rate`: `wins / (wins + losses) * 100` (filtering for `CLOSED_WIN` and `CLOSED_LOSS`).
     * `net_r`: sum of `realized_pnl` where status is in `CLOSED_WIN`, `CLOSED_LOSS`, `CLOSED_AT_EXPIRY`.
     * `approval_rate`: `count(mas_approval_status == 'APPROVED') / count(all session entries in window) * 100`.
* **Response JSON Format**:
  ```json
  {
  ```

### 5. `POST /api/v1/system/analysis`
Handles ad-hoc natural language queries for diagnostic audits.
* **Authentication**: Required (is_logged_in == True)
* **SQL/Logic Steps**:
  1. Validate request body contains non-empty `query` string.
  2. Generate UUID `analysis_id` and write initial pending record to `system_analysis_reports`.
  3. Compile context data from database layers:
     - Param values.
     - Trades summary stats (count, wins, losses, total R) from past 30 days.

  5. Run LLM task using `agent_core._call_from_spec("system_analysis", context_text=prompt)`.

## 7. Execution and Verification Plan
1. **Database migrations**: Add new `SystemAnalysisReport` model to `database.py`. The existing `init_db()` is called during startup, which will automatically create the table.
2. **Registry Injection**: Add `scheduler_health_registry` at the top level of `main.py` and modify loops to update status/timestamps.
3. **Endpoint implementation**: Create a new API router or add endpoints directly to `main.py`.
4. **Verification**:
   - Run the unified server: `python main.py` or through uvicorn.
   - Run the diagnostic test suite to ensure no regressions: `python harness/test_audit_safety.py`.
   - Call endpoints via cURL or local HTTP requests to verify outputs match specs.
