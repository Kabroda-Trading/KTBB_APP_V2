## 2. Logic Chain
1.  **FastAPI E2E Execution**: Since the application lifespan starts asynchronous scheduler loops that perform exchange I/O and write to the database (Observation 3), executing E2E tests in-process using `FastAPI.testclient.TestClient` will trigger these loops on the same event loop. This leads to database pollution and API call failures if the server is in testing mode.
2.  **Database state isolation**: Since database connection is instantiated at module import time using the environment variable `DATABASE_URL` (Observation 2), spawning the server in a separate subprocess with the environment variable set to `DATABASE_URL=sqlite:///./kabroda_test.db` cleanly isolates database access. Schedulers and route handlers will write to the test DB without interfering with the live `kabroda.db` database.
3.  **Authentication**: To invoke auth-restricted endpoints (such as `GET /api/v1/system/state`), the E2E test client can seed a test user inside `kabroda_test.db` with a known password hash generated by `auth.hash_password()`, send a `POST /login` form request, capture the signed session cookie (Observation 1), and present it on subsequent HTTP queries.

## 3. Caveats
- **Background API Calls**: We assume the test suite will run in "offline" mode or have a stub/environment flag (`OFFLINE_TEST=True`) to prevent background loops from attempting live exchange operations during test execution. If background calls cannot be stubbed, they might throw network errors.
- **LLM / AI Mocking**: Tier 1 and 2 tests targeting the AI analysis endpoint (`POST /api/v1/system/analysis`) assume a mock or fallback deterministic analyzer is configured when LLM API keys are absent, preventing API cost or timeouts.
